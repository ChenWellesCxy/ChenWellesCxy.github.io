独立实现 CoverageModel：从规范需求到可维护的验证模型

项目文档快照 · 2026-10-21 · 查看原文 ↗

这份路线图的目标是让你最终能独立设计并实现一套 CoverageModel，而不是只会读或修改别人生成的 SV。你有 DRAM/FineSim 项目经验，已经熟悉命令、bank、MR 与时序约束；需要补齐的是把这些协议知识转成可追踪的数据模型、采样器、检查器和覆盖模型的工程方法。

权威边界：参考实现不是协议规范

RefProject/.../新版/SV文件 下的 LPDDR6 代码是他人提供的实现与学习素材。它能展示一种 SV 组织方式，也能让你看到复杂命令采样、状态派生和 coverage 的代码规模，但它不是 JEDEC 规范的替代品，也不能单凭生成代码名称证明协议含义正确。

实现时请按以下证据顺序决策：

  1. 适用版本的正式协议规范、勘误和项目认可的设计/验证需求：定义命令编码、合法状态转换、时序值、例外模式及配置条件。遵循团队规定的保密与访问要求；不要把受限规范上传到个人 GitHub 或公开仓库。
  2. 经过评审的项目决策与验证计划：记录规范未覆盖、解释存在分歧或由芯片实现限定的行为，并明确批准人/版本。
  3. RTL、现存 testbench 与历史 pattern 的观测行为：帮助理解 DUT 接口和已有工程约定，但若与批准需求冲突，应提出问题，不能悄悄把现状当作规范。
  4. 参考 CoverageModel 与开源示例：作为架构/语法例子；逐条追溯其假设与输入，再决定是否采用。

每一条 checker 和 coverpoint 都要能回答：“这来自哪条批准需求？”这条追踪关系比生成器复杂度或 coverage 百分比更重要。

总体数据流

规范条目/验证需求
        │  拆成可验证的规则、模式、边界和豁免
        ▼
需求追踪表 ───────────────► directed/random stimulus + reference checks
        │                                  │
        ▼                                  ▼
事务/协议数据模型 ◄────── pin sampling / transaction monitor
        │                                  │
        ├── 命令译码与合法性 ──────────────┘
        ├── 每 bank / rank / mode 状态
        ├── 时序历史与约束检查
        └── 可解释的命令/状态/时序 coverage
                         │
                         ▼
            回归、波形、报告、失败复现
                         │
                         └────► 模型修正与需求追踪更新

生成器是后续的实现手段，不应成为流程起点。先验证少量手写规则的语义和测试，再抽象稳定的重复结构。

第一步：把需求写成可验收的规则

不要从“覆盖所有 timing”这种大目标直接开始编码。每条需求写成一行可检查的条目，至少包含：

字段 例子（仅教学抽象）
ID / 来源 BANK-RD-001 / 经批准的协议需求编号
前置状态 目标 bank 已由 ACT 打开
触发事件 收到对同一 bank 的 RD
规则 ACT 到 RD 的间隔不得小于配置的 tRCD
单位与边界 使用明确的 CK cycle 计数；等于边界是否合法
模式条件 速率/模式/子通道条件，或明确“不适用”
检查动作 接受/报告违规；错误码和报告上下文
coverage 目标 低于边界、恰好边界、超过边界（若各场景均有意义）
验证证据 定向向量、断言/scoreboard 结果、coverage bin

真实 DRAM 参数、命令前置条件、例外项和单位只能从适用规范与批准需求中填入，不能照抄教学例子。需求里含模糊词如“足够等待”时，应先澄清单位、取整方法、开闭区间、模式切换时生效的值及复位行为，再编码。

第二步：确定最小且完整的数据模型

先画对象与作用域，避免状态变量只有名字没有生命周期：

  • Command event：一次已译码命令的时间戳、命令种类、目标 rank/sub-channel/bank group/bank、行列地址、模式/标志、原始采样引用、有效性与无效原因。
  • 采样 raw sample：物理引脚各采样相位、边沿/周期信息及未知值信息；保留它便于解释 decoder 为什么作出某个判断。
  • Bank state：每个 bank 的 open/closed、当前行、最近 ACT/PRE/RD/WR 等历史时间；明确状态是 per-rank、per-sub-channel 还是跨域共享。
  • Timing context：规范参数的来源、当前配置、换算后的整数单位、取整方向和是否已初始化。尽可能将单位集中，不在各 checker 中混用 realtime、ps 和 cycle。
  • Violation record：规则 ID、起止命令、实际间隔、要求间隔、目标层级与时间，确保一条失败能直接定位波形和需求。
  • Coverage view：只包含你要统计的可观察场景，和状态/checker 数据之间有清楚定义；不要把 covergroup 变量当唯一状态存储。

SV 落地可以先用 typedef enum 表示命令、typedef struct packed/unpacked 表示 event/record、package 共享类型。先明确字段语义和初始化，再决定 class、interface、event 或 virtual interface。不要为了像 UVM 而过早引入 factory、config_db 或大量 class 层次。

小型教学模型（不是 JEDEC 命令协议）

本学习项目的 labs/04_coverage/tb.sv 会构造一个教学命令集，简化为 ACT、RD、PRE。它用于练“事件 + 同 bank 的 tRCD 间隔 + 边界计数”，不模拟真实 CA 编码，也不代表 JEDEC 的命令格式或全部时序行为。

概念上，模型接收 ACT(bank) 时保存该 bank 的打开周期 act_cycle[bank]；收到同 bank 的 RD 时计算：

elapsed = current_cycle - act_cycle[bank]
legal   = bank_is_open[bank] && elapsed >= teaching_tRCD

PRE(bank) 关闭该 bank。测试至少安排 elapsed = tRCD - 1、elapsed = tRCD、elapsed = tRCD + 1，并确认同 bank 与不同 bank 的历史不会串用。这个示例具体边界只对教学模型成立；真正项目应从权威需求定义比较符号、事件计数时点和重开/关闭语义。

第三步：设计采样层，分清引脚与事务

采样层回答“什么时候、从哪些物理量构造观察记录”，不负责替协议规范作判断。

  1. 固定采样时钟/边沿和复位语义；说清楚 reset 期间是否丢弃样本，X/Z 信号怎样处理。
  2. 如果命令由多个边沿/周期组成，保留每一相位和有效性；不要在相位不完整时制造一个貌似合法的事务。
  3. 标记 sub-channel/rank 等物理来源，避免交错流互相污染。
  4. 先输出 raw sample 或明确的 invalid record，再让 decoder 作语义判定；避免采样器一边猜命令、一边改协议状态。
  5. 通过可控 stimulus 验证边沿和相位：单个输入变化应在预期时间只产生一次观测。

若架构基于 transaction-level 输入而不是 pins，也要定义 transaction 的产生者和时序语义；不能因为 stimulus 已给出 RD 就省略 monitor 对 DUT 实际行为的观察，除非验证目标明确只测模型本身。

第四步：命令译码与错误隔离

把译码拆成可单测的步骤：

  1. 采样合法性：必要相位齐全、相关 bits 已知、采样序号完整。
  2. 编码匹配：由规范表把原始字段映射到候选命令。
  3. 操作数提取：抽取 bank、地址、模式等字段。
  4. 上下文补全：只在规范定义的多拍命令确实满足前序条件时组合字段。
  5. 资格判定：rank/channel/filter 等观测范围限定。
  6. 结果发布：生成 immutable-by-convention event，附上 valid、原因码和原始观测引用。

对 unknown、illegal encoding、丢相位、X/Z、复位重入及重叠事务分别定义行为。未知命令不能被静默映射成 NOP；否则可能丢掉真实失败，也会错误提高 coverage。每个失败至少能区分“物理采样不完整”“编码不识别”“被明确 filter”三种原因。

第五步：事件、状态和调度规则

事件负责通知消费者某个阶段已发生，transaction/event 才携带数据。先写明顺序契约，例如：

采样记录完成 → decoder 返回 event → event 放入队列/稳定变量
→ 状态模型消费 event → checker 计算并报告 → coverage 按已定义的采样快照记录

SV 中多个 always @(same_event) 会在同一仿真时间步醒来，过程之间没有可依赖的执行先后。若 coverpoint 既读取本次 event，又读取由另一个 listener 刚更新的状态，就可能产生 race。应通过明确阶段（例如一个集中 dispatcher 顺序调用状态/check/coverage task、clocking block、队列消费或后续采样事件）制定稳定契约，并以波形/仿真器支持情况验证。单纯把多个过程挂在同一事件上不等于建立先后顺序。

状态更新应由一个明确 owner 执行，定义：

  • reset 初值和复位中断的事务如何清理；
  • 状态转移的先决条件与失败行为；
  • bank/rank/channel 的索引域；
  • 合法命令与违规命令是否仍更新状态（依需求决策）；
  • 一次 event 是否可以多次消费，如何防止重复更新。

建议先实现单 bank，再扩成数组和多 sub-channel。把“状态更新”和“断言违规”职责分开：看到非法命令后究竟保持旧状态、标记未知还是按模型恢复，必须一致并可解释。

第六步：timing 检查器

每条 timing rule 写成通用接口：check(rule_id, start_event, end_event, context)，但在引入抽象前先用 1–2 条手写规则验证架构。

重点边界：

  • 单位：cycle 计数还是时间单位；时钟切换后旧时间戳如何解释。
  • 取整：从 ns/ps 换算周期时，向上/向下/最近取整分别有什么规范依据。
  • 边界包含性：>= min、> min、<= max 或窗口区间；恰好等于边界必须有专门定向测试。
  • 历史来源：前序事件必须与目标 bank/rank/channel 匹配；不能取全局“最近一次 ACT”。
  • 配置变化：使用起点配置、终点配置还是当前生效配置；需求要给答案。
  • 缺少历史：例如没观察到对应 ACT 时，是跳过规则还是报模型同步错误，要分开定义。
  • 错误输出：同时打印 rule ID、需求追踪 ID、两端事件、差值、期望值和单位。

先用独立纯函数计算差值/合法性，再接到 event 流；这样能在不启动整套 TB 的情况下验证单位与边界算法。

第七步：functional coverage 设计

coverage 是“刺激/监控实际观察了什么”的摘要，不是协议正确性的证明，也不替代 checker。

从验证计划反推 coverage：

  • 命令覆盖：命令类型与合法操作数；只在字段语义有效时采样。
  • 状态覆盖：从哪些状态进入/退出，是否观察到恢复/边界状态。
  • 时序覆盖：至少覆盖边界附近的区间，如 below/equal/above（仅当该场景对规则有定义）。
  • 交叉覆盖：只对有验证意义且 stimulus 可达到的维度做 cross，并控制 bins 数量。
  • 排除项：明确 ignore/illegal bin 的理由及需求依据，避免通过忽略难点让 coverage 好看。
  • 覆盖目标：每个 bin 绑定一个场景或需求 ID；无法达到的 bin 要分析，而非直接 waive。

采样时机要和状态契约一致。针对上面的教学 ACT/RD/PRE 模型，可记录命令种类、bank 与 RD 间隔类别；边界计数由独立定向刺激保证，checker 结果保证模型接受/拒绝正确，coverage 再确认三个类别确实都观察到了。

第八步：何时做生成器

生成器适合把稳定、规则化、可校验的重复数据转成代码，例如多组相同结构的 bins 或查表函数。先保持输入声明性：每个规则至少有 ID、源需求、适用条件、单位、范围、处理策略、coverage 目标。

生成器要分层：

  1. 输入 schema 和语义校验（缺字段、未知策略、区间重叠、单位不匹配时拒绝生成）。
  2. 规范化中间表示（IR），保留来源与追踪信息。
  3. SV renderer（只负责输出语法，不重新解释需求）。
  4. 输出检查（格式/编译/规则数量/重复 ID/生成文件差异）。
  5. 可重复性（同输入产生相同输出；生成器版本和输入摘要进入报告）。

不要一开始就生成庞大 interface。优先生成“数据”和重复 coverpoint；采样时序、复杂状态转移、例外处理先用手写且可审阅的代码。生成结果必须可回溯到输入行/需求 ID，并能由小型 golden tests 检查。需要人工判断的含义不应隐藏在模板字符串里。

第九步：验证与验收矩阵

至少用四层证据：

层次 验证什么 通过证据
单元测试 译码、索引、单位换算、边界比较 正常值、最小/最大、未知值与非法值定向向量
模型测试 状态转移、bank 隔离、reset 事件序列后状态符合预期，重复/丢失事件能检测
checker 测试 合法/违规时序 below/equal/above 明确得到预期结果；失败报告可追踪
coverage 测试 bin 与交叉是否被实际采到 对照测试清单逐项命中；未命中场景可解释
仿真/波形 采样点、事件顺序、race、复位 波形中的输入、event、状态、结果对得上
生成器测试 输入校验、稳定输出、可追踪 schema 拒绝错误输入；重复生成无意外 diff；生成代码编译
回归/维护 参数组合、模式、并行配置 固定 seed 可复现；每个失败有摘要和可定位日志

一个 rule 的验收不能只是“编译通过”。最小闭环应是：需求 ID → 定向场景 → monitor event → 状态/时序结果 → assertion/checker 报告 → coverage hit → 可复现波形。

推荐的交付物结构

coverage_model/
  requirements/       # 追踪表或经过批准的规则输入
  sv/                 # 手写类型、monitor、状态、checker、coverage
  generator/          # 后续稳定后再加入
  tests/              # 单元、规则边界、coverage smoke、golden tests
  wave/               # 小型回归的波形配置与阅读说明
  README.md           # 编译器、源文件顺序、运行命令、已知限制
  traceability.csv    # 需求 ID → 实现 → 测试 → coverage 的映射

实际工作项目需遵守公司仓库布局和数据保密规则；这里是学习时可借鉴的分层建议。

与学习实验的关系

当前教学闭环会逐步从 SV 基础和 coverage 小模型开始。labs/04_coverage/tb.sv 是其中一个刻意缩小的实验：它使用教学版 ACT/RD/PRE 命令，练习命令事件、同 bank 的 tRCD 间隔判断和边界计数。它不是 JEDEC 命令或 timing 的权威实现，也不应用于真实 DRAM 功能判断。每次讲解时都要把“教学协议约定”和“真实规范结论”分开写。

读参考项目的目标，是看懂大型代码如何组织，以及练习追踪事件与 coverage；独立实现的目标，则是你能从权威需求出发，解释每个字段、状态更新、边界条件、报告和 coverage bin 为什么存在。最终面试时，展示你能说清楚需求依据、模型边界、仿真调度和失败定位，比声称“看过一个很大的生成器”更有说服力。
