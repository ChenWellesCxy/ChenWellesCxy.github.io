SystemVerilog 官方文档详解：验证篇

项目文档快照 · 2026-10-21 · 查看原文 ↗

这份教程面向已经会读 DRAM 命令和仿真波形、但很少写 SystemVerilog 的验证工程师。目标是把 class、随机约束、并发、接口、断言和功能覆盖率连成一套能解释、能调试的验证代码。

这里的代码例子是为教学原创编写的 SystemVerilog 片段。它们用于说明语言语义，不构成 JEDEC 命令编码、DRAM 时序或产品验证规范；示例未经仿真器实跑，具体工具支持和编译选项需要按目标仿真器确认。完整协议模型必须以批准的协议规范、项目验证计划和实现约定为依据。

怎样使用官方资料

SystemVerilog 的规范性定义以 IEEE Std 1800-2023 官方页面 与其引用的 LRM 为准。IEEE 将 1800 描述为涵盖硬件设计、testbench、coverage、assertions、面向对象、约束随机验证以及外部语言 API 的统一语言标准；该页面提供 IEEE Get Program 的访问入口。Accellera 也介绍过与 IEEE 合作，通过 Get Program 向全球工程师开放 IEEE 1800 的标准访问。Accellera 说明

Accellera 的 SystemVerilog Assertions 教程与讲义适合理解 SVA 规划、采样/求值区域、属性重用和调试思路；它是学习资料，不取代当前 IEEE 标准。Accellera 关于 clocking block 的说明材料能帮助理解时钟同步接口和 skew，但文档较早，涉及具体语义时仍要对照 1800-2023。工具兼容性则查你实际使用的版本，例如 AMD Vivado 仿真器的 SystemVerilog 支持表：厂商文档能说明该工具支持哪些语言特性，不能作为所有工具都一致支持的保证。

推荐遇到疑问时先定位 LRM 主题，而不是只搜语法片段：classes / inheritance / virtual methods / randomization / constraint blocks / processes / mailboxes / semaphores / interfaces / clocking blocks / scheduling semantics / assertions / functional coverage / packages / compilation units / bind / DPI / VPI。标准负责定义语义；工具手册负责说明本版本支持范围；工程规范负责决定项目如何使用这些特性。

1. class：把一次事务和操作放在一起

1.1 对象句柄、属性和方法

class 定义对象类型；变量 tr 通常保存对象句柄。对 class 类型变量做赋值会复制句柄，不会自动克隆对象。

module class_handle_demo;
  typedef enum bit [1:0] {ACT, RD, PRE} teach_cmd_e;

class teach_item;
  rand teach_cmd_e cmd;
  rand bit [1:0] bank;
  rand bit [5:0] addr;
  int unsigned serial;

  function new(int unsigned serial = 0);
    this.serial = serial;
  endfunction

  function string convert2string();
    return $sformatf("id=%0d cmd=%s bank=%0d addr=%0h",
                     serial, cmd.name(), bank, addr);
  endfunction
endclass

teach_item a, b;
initial begin
  a = new(1);
  b = a;                 // b 与 a 指向同一个对象
  b.bank = 2;
  $display("a.bank=%0d", a.bank); // 2
end
endmodule

this 是当前对象句柄；new 是构造函数，用于初始化新分配对象。class 句柄初值为 null，在解引用之前应检查是否已构造。构造函数可有默认参数，构造派生类时通常需要显式调用 super.new(...) 来初始化父类部分。对象成员的缺省值不是业务状态设计的替代品；在复位、无效地址、未初始化时间戳等场景要显式建立约定。

常见误区： b=a 不是复制 a 里的字段，而是让 a 和 b 指向同一对象。多个组件持有同一 transaction 句柄时，生产者之后再改字段会影响消费者已保存的“历史记录”。要么约定发布后不可变，要么复制/克隆。

1.2 继承、virtual 与动态派发

继承让派生类获得父类的状态和方法；重写方法要声明为 virtual，这样经由父类句柄调用时，才会根据对象真实类型动态选择实现。

module polymorphism_demo;
  virtual class command_item;
  pure virtual function string kind();
  virtual function bit is_column_cmd();
    return 0;
  endfunction
endclass

class read_item extends command_item;
  bit [1:0] bank;
  bit [5:0] column;

  function string kind();
    return "READ";
  endfunction
  virtual function bit is_column_cmd();
    return 1;
  endfunction
endclass

command_item item;
read_item concrete;
initial begin
  concrete = new();
  item = concrete;
  $display("%s column=%0d", item.kind(), item.is_column_cmd());
end
endmodule

virtual class 是抽象基类，不能直接实例化。pure virtual function 只给出接口声明，没有函数体；具体非抽象派生类必须实现它。普通 virtual function 可以提供默认实现，派生类可以重写。多态的用途是让 sequencer、scoreboard 或 reporter 面向通用 transaction 接口，不用每个地方都判断具体子类。

陷阱： 若通过父类句柄调用一个非 virtual 方法，会静态选择父类版本，即使句柄实际指向派生对象。不要把“用了继承”误当作“实现了动态派发”。纯虚函数也不能像普通函数那样只在某处临时省略实现；抽象接口约束的是具体类的完整实现。

1.3 参数化 class

参数化类可以按类型或常量配置复用结构，例如不同位宽的 FIFO。类型参数用 type 声明，值参数写类型和默认值。

class tiny_fifo #(type T = int, int DEPTH = 4);
  local T data[DEPTH];
  int unsigned wr, rd, count;

  function bit push(T value);
    if (count == DEPTH) return 0;
    data[wr] = value;
    wr = (wr + 1) % DEPTH;
    count++;
    return 1;
  endfunction
endclass

tiny_fifo #(teach_item, 8) item_q;

参数化实例是在 elaboration/编译阶段按特定参数形成的专用类型。检查数组尺寸、索引位宽和 % DEPTH 的零深度边界；实际参数不应允许非法值。更复杂的泛型 API 可使用 parameterized class/interface，但语法和工具支持要在目标 simulator 上确认。

1.4 浅拷贝和深拷贝

简单句柄赋值只复制引用。struct/数组整体赋值可按其成员语义复制值，但里面若含 class handle，内部句柄仍是引用；所以“struct 赋值了”也未必实现深拷贝。

class command;
  rand bit [1:0] bank;
  rand bit [5:0] addr;
  function command clone();
    command c = new();
    c.bank = this.bank;
    c.addr = this.addr;
    return c;
  endfunction
endclass

class packet;
  command header;
  command payload;
  function packet clone();
    packet p = new();
    if (header  != null) p.header  = header.clone();
    if (payload != null) p.payload = payload.clone();
    return p;
  endfunction
endclass

深拷贝要递归考虑 dynamic array、queue、嵌套对象、共享对象关系、null 和循环引用。若两个字段原来有意指向同一个子对象，简单递归 clone 可能把共享关系拆成两个对象。生产代码最好定义明确的 copy/clone 契约：哪些字段复制、哪些 handle 共享、哪些 ID 必须重生。不要把自定义 copy() 与 UVM 的 copy 机制混为一谈。

练习：添加 bank_state 子对象，让 packet.clone() 深拷贝它；验证改副本不会改原对象。答案线索：逐个检查所有 class handle 字段，不能只依靠最外层句柄赋值。

2. 约束随机：描述合法集合，而不是随机拼比特

2.1 rand、constraint 与失败处理

rand 声明由 randomize() 求解的成员；randc 请求循环随机行为。普通属性作为 state variable，可在约束中引用但不会被 randomize() 改写。

module constraint_demo;
  typedef enum bit [1:0] {ACT, RD, PRE} teach_cmd_e;
  class teach_item;
    rand teach_cmd_e cmd;
    rand bit [1:0] bank;
    rand bit [5:0] addr;
    int unsigned open_bank_mask;

    constraint legal_cmd_c { cmd inside {ACT, RD, PRE}; }
    constraint bank_c      { bank inside {[0:3]}; }
    constraint addr_c {
      if (cmd == ACT) addr inside {[0:47]};
      if (cmd == RD)  addr[5:3] == 0;
    }
    constraint open_bank_c {
      if (cmd == RD) open_bank_mask[bank] == 1;
    }
  endclass

  teach_item tr;
  initial begin
    tr = new();
    if (!tr.randomize())
      $error("unsatisfiable constraints");
  end
endmodule

求解器寻找满足所有启用约束的取值；它不是按程序里的语句逐行赋值，也不保证你期望的概率分布。随机变量通常在约束求解中按二态值处理，即使目标字段定义为四态类型也不要期望约束求解器随机生成 X/Z。调用返回 0 要显式处理，并记录当前模式、约束开关和 seed，不能把失败值继续送 DUT。

2.2 集合、范围和动态数组

inside 表示集合成员，范围端点包含在集合中。foreach 为数组每个索引展开约束；unique 对列出的元素施加两两不同约束。

class burst;
  rand bit [7:0] length;
  rand bit [2:0] beats[4];
  constraint length_c { length inside {8, 16, [24:32]}; }
  constraint beats_c {
    foreach (beats[i]) beats[i] inside {[0:5]};
    unique {beats};
  }
endclass

数组维度和 size 本身要明确随机还是固定。对动态数组先约束 .size()，再用 foreach 约束元素；注意索引顺序和空数组时的行为。unique 不是“让 simulator 尽量不同”，而是硬约束；取值域容量不足会导致求解失败。

2.3 dist：概率权重不是覆盖保证

dist 为合法值设置相对权重：value := weight 将权重赋给范围内每一个值；value :/ weight 把该权重分摊到范围内的值。实际抽样分布是权重表达的分布意图，需考虑其它约束、工具求解器和大量样本验证；不应把它当作 coverage 的保证。

constraint command_mix_c {
  cmd dist { ACT := 2, RD := 6, PRE := 2 };
}

陷阱： 若 cmd 受状态约束而某些命令不可选，统计结果自然不会符合裸 dist 比例。验证计划若要求精确场景比例，应通过测试调度/计数控制和报告，而不是只在随机类里设权重。

2.4 solve before 的作用

默认约束系统尽可能以解集合为整体求解；solve a before b 指定求解顺序，可改变解的分布倾向，但不会把 a 和 b 变成时序上的先后动作，也不会创建 sequence。

class sized_cmd;
  rand bit [1:0] kind;
  rand bit [7:0] len;
  constraint legal_c {
    kind inside {0, 1};
    if (kind == 0) len inside {[1:4]};
    else           len inside {[1:12]};
  }
  constraint order_c { solve kind before len; }
endclass

没有 solve before 时，len 可行组合多的类型可能在抽样概率上占优势。若测试意图是先选择 command kind，再按该种类的长度域采样，solve before 才可能是恰当的分布控制。先定义希望的概率，再与工具统计结果核对；不要用它修复互相矛盾的硬约束。

2.5 soft、inline constraint 和模式开关

soft 表达偏好/默认条件，遇到冲突时可被其它硬约束覆盖；它让 reusable item 有默认行为，但调用者可在 inline constraint 中收窄场景。

module soft_inline_demo;
  class item;
    rand bit [1:0] cmd;
    constraint default_cmd_c { soft cmd == 1; }
  endclass

  item tr;
  initial begin
    tr = new();
    if (!tr.randomize() with { cmd == 2; })
      $error("randomization failed");
  end
endmodule

randomize() with { ... } 为这次随机调用增加临时约束。rand_mode(0) 停止某字段随机更新，使当前值作为状态值参与约束；但关联约束仍可能限制其它随机字段。constraint_mode(0) 则关闭某整个 constraint block。两种开关职责不同。恢复模式时要在同一调用路径配对开启；随机失败时打印 mode 状态。soft 冲突的处理不适合用含糊默认值替代测试场景设计，复杂冲突请查当前 LRM 和工具行为。

2.6 randc 与 pre/post_randomize

randc 对单个随机变量提供无重复循环的随机次序语义，直到可选值循环完成再开始新一轮。它不是全局覆盖保证，也不能保证复杂多字段组合都先各出现一次。循环池受域和约束影响；如果每次约束变化，需检查当前可行值集合。

class bank_selector;
  randc bit [1:0] bank;
  function void pre_randomize();
    // 在本次求解前准备非随机上下文
  endfunction
  function void post_randomize();
    // 只做轻量派生/日志，不要偷偷改坏刚求出的约束结果
  endfunction
endclass

pre_randomize() 在随机化前调用，post_randomize() 在成功完成随机化之后调用。不要把 DUT 驱动、时间控制或不可逆外部副作用塞进 callback；失败时不得假定 post callback 帮你清理。派生字段可在 post_randomize() 计算，但若这些字段也影响合法性，应在 constraint 中建模，而非事后改值绕过 solver。

练习：为 ACT/RD/PRE 设置可达约束；让 RD 只在 bank 打开时出现；然后用 inline constraint 固定同一个 bank，并故意固定一个互相矛盾的条件。答案线索：randomize() 应返回失败；检查它，而非读取陈旧 transaction。

3. 并发：process、event、mailbox、semaphore

3.1 process 与生命周期

fork...join 创建并行子过程。join 等所有子过程完成；join_any 等第一个完成后父过程继续，但其它子过程仍运行；join_none 不等待，父过程继续。取消或等待策略要精确，否则后台 driver/monitor 会在测试结束后继续操作信号。

initial begin
  fork
    begin : isolated_controller
      fork
        begin
          #1000ns;
          $error("timeout");
        end
        begin
          run_test_sequence();
        end
      join_any
      disable fork; // 只取消 isolated_controller 子进程中尚未结束的工作
    end
    begin : unrelated_monitor
      forever begin
        #100ns;
        sample_background_status();
      end
    end
  join_none
end

disable fork 会终止执行该语句的进程所拥有的活动后代进程；具名 block/task 只是命名和组织代码，并不会隔离动态父子关系。要保护同一上层进程中的旁支，应让要取消的并发工作位于一个独立子进程中，并在该子进程内部创建并取消自己的 inner fork，如上例 isolated_controller。外层 unrelated_monitor 是另一个兄弟进程，不属于 controller 的后代，因此不会被内层 disable fork 取消。也可以保存 process handle，只终止明确选定的进程。process class 提供对进程状态/生命周期的程序化控制，可保存 process::self() handle，查询 status 或 kill/suspend/resume；这些操作需设计清楚谁拥有终止权。

请注意一个声明初始化的生命周期细节：command c = new() 和 packet p = new() 位于 class methods 中；class methods 默认 automatic，因此每次 clone() 调用都有自己的局部句柄。teach_item tr = new() 若声明在 module scope，则是静态 module 变量的初始化；若放进 static task/block 的局部声明中，初始化不是每次进入时重跑。需要每次重新初始化的局部对象应放在 automatic task/function 中，或显式在每次调用/循环体执行时赋值。下面的 stimulus 片段中通过 module 变量声明、initial 赋值或 automatic task 避免把“一次初始化”误读成“每次自动重置”。

automatic 变量生命周期和 fork 子过程捕获变量的时机也是常见坑。initial/module 作用域的声明通常具有 static lifetime；若在 static block 中写带初始化的局部声明，初始化通常只发生一次，而不是每次进入该 block 都重新赋值。task/function 也要检查其声明是 static 还是 automatic；class methods 默认 automatic。循环启动并发线程时，为每个线程建立独立索引副本，避免所有线程最终看见循环结束值。需要每次调用重新创建局部对象时，可用 task automatic 并把初始化放在该调用作用域中。

3.2 event：通知不携带数据

命名 event 是同步通知；它不保存 transaction payload，也不是可计数队列。

event item_ready;

initial begin
  @item_ready;                // 等待将来的触发
  $display("notification seen");
end

initial begin
  #10ns;
  -> item_ready;              // 触发事件
end

若事件在消费者开始等待前已经触发，单纯 @item_ready 可能错过通知。wait(item_ready.triggered) 可用于同一仿真时间步触发状态的等待模式；仍要明确事件何时触发、数据何时稳定。->> 是非阻塞事件触发形式，调度时机与 -> 不同，只有理解当前时间步的调度语义后再使用。

对于“每次命令都要被消费”的需求，用 mailbox/queue 传 transaction 通常比裸 event 更可靠：event 表示“发生过”，mailbox 保存多个待处理对象。event payload 的关联常见 race：先赋值 transaction 再触发，多个生产者时还要避免共享变量被覆盖。

3.3 mailbox：带队列语义的进程间通信

mailbox 是内建 class，可参数化存放类型；无界 mailbox 的 put 不等待容量，定长 mailbox 满时 put 会阻塞至有空间。get 在队列空时阻塞，try_get 非阻塞并通过返回值报告是否取到。

module mailbox_demo;
  class mail_item;
    int value;
  endclass

  mailbox #(mail_item) observed = new();

  task automatic producer();
    mail_item tr;
    tr = new();
    tr.value = 7;
    observed.put(tr); // 发布后不再修改 tr
  endtask

  task automatic consumer();
    mail_item got;
    observed.get(got); // 空时等待
    $display("value=%0d", got.value);
  endtask

  initial fork
    producer();
    consumer();
  join
endmodule

重要约定：通常 mailbox 传的是 class handle，不是自动快照。producer put(tr) 后如果还修改 tr，consumer 可能看到新值。发布后不可变或发送 clone。多生产者时，如果顺序具有协议意义，应把 timestamp/sequence ID 放进对象并在 consumer 验序。

3.4 semaphore：限制并发资源

semaphore 是 key bucket，用于控制资源并发数；get(n) 取得 n 个 key，key 不足时阻塞；put(n) 归还。一个 key 可实现简单互斥锁。

semaphore bus_lock = new(1);

task automatic drive_shared_bus();
  bus_lock.get(1);
  // 在这里独占总线资源
  bus_lock.put(1);
endtask

每个成功 get 路径都应确保 put，包括异常/提前退出路径；否则其它线程永久阻塞。semaphore 只保护你明确包住的临界区，不会自动给共享变量加锁。避免把长时间等待放在锁内。

练习：两个并发 driver 通过 mailbox 给 monitor 发 item，另用 semaphore 保护共用的打印序号。构造故意延迟的 producer 检查次序。答案线索：对比 event、mailbox、semaphore 各自解决的是通知、数据排队、资源互斥。

4. interface、modport、virtual interface 和 clocking block

4.1 interface 与 modport

interface 把一组信号和与其有关的任务/时钟访问集中定义。modport 为不同角色规定方向/可见操作，减少 TB 和 DUT 对信号方向的误解。

interface simple_if(input logic clk);
  logic req, gnt;
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output req;
    input  gnt;
  endclocking
  modport DUT (input clk, req, output gnt);
  modport TB  (clocking drv_cb, input clk);
endinterface

module 可以用 simple_if.DUT bus 接口端口。modport 不是新的物理信号，也不会验证协议时序；它表达连接角色的访问规则。接口中可封装 assertion、driver/monitor tasks 和 clocking block，但保持边界清晰：信号定义、TB 驱动、协议检查可分区维护。

4.2 virtual interface

class 本身不能直接拥有静态层次端口引用；virtual interface 是指向某个已实例化 interface 的句柄，供 class-based driver/monitor 使用。

class simple_driver;
  virtual simple_if.TB vif;
  function new(virtual simple_if.TB vif);
    this.vif = vif;
  endfunction
  task send_req();
    @(vif.drv_cb);
    vif.drv_cb.req <= 1'b1;
    do @(vif.drv_cb); while (!vif.drv_cb.gnt);
    vif.drv_cb.req <= 1'b0;
  endtask
endclass

创建 driver 前要把具体 interface instance 传进来；使用前检查 handle 是否已赋值。多个 agent 可能绑定不同接口实例，所以不要在 class 里硬编码 top.dut... 层次路径。参数化 interface 的 virtual handle 类型必须匹配参数与 modport。

4.3 clocking block 与 #1step

clocking block 声明某时钟域中信号如何采样和驱动，减少 testbench 与 RTL 同一边沿同时读写导致的 race。input #1step 表示在采样时钟事件前一个全局仿真精度 step 采样，可理解为取边沿到来之前稳定的值；它不是“延迟一个完整时钟周期”。clocking block 默认 input skew 是 #1step，但教学代码应显式写出 skew，让协议意图清楚。clocking output 的驱动按 clocking block 的驱动调度语义进行，不能把它等同于在任意 always 块里用普通 blocking assignment。

示意时序：

上一个时刻             clocking event                    后续驱动/RTL响应
    │                       │                                  │
    ├── input #1step 采样 ───┤                                  │
                            └── output skew 决定 TB 驱动时机 ───┘

#1step 和 #0 是不同语义；不要用 #0 当通用“等 NBA 完成”方法。并发读写仍需结合 SystemVerilog event regions 分析。对于 DRAM 命令总线，先约定 CA 在哪个边沿稳定、TB 在哪个 skew 驱动、monitor 在哪个点采样，再画波形验证。

练习：把无 clocking block 的 @(posedge clk); req = ...; driver 改为 clocking block 方式；比较在同一边沿 drive 与 sample 的值。答案线索：考虑驱动端、DUT sequential block、monitor 采样各自执行区域，而非仅看源码先后。

5. SVA：把时序需求写成可定位的属性

5.1 sequence、property 与断言

sequence 描述信号/事件的时序片段；property 把片段组合成要检查的逻辑关系；assert property 在仿真/形式环境中检查，cover property 观察场景是否出现。concurrent assertion 有 clocking event，以采样值求值。

property req_gets_gnt;
  @(posedge clk) disable iff (!rst_n)
    req |-> ##[1:3] gnt;
endproperty

p_req_gets_gnt: assert property (req_gets_gnt)
  else $error("request did not receive grant in 1..3 cycles");

此例要求在某个采样时钟观察到 req 后，1 到 3 个时钟周期内看到 gnt。|-> overlapped implication 表示 consequent 的起点与 antecedent match 终点同一采样点；|=> non-overlapped implication 从下一个采样点开始。##n 表示采样时钟周期延迟，##[m:n] 表示区间延迟。

5.2 sampled values、$past 与 vacuity

并发断言表达式使用采样值，不是执行 action block 时实时读取的任意当前值。通常在时钟边沿的 Preponed 区采样，在 Observed 区求值，action block 在 Reactive 区执行。Accellera 的 SVA 讲义明确画出这一采样/求值/动作关系。官方讲义

property stable_while_waiting;
  @(posedge clk) disable iff (!rst_n)
    req && !gnt |=> $stable(addr);
endproperty

$past(expr) 访问前一采样时刻的值；仿真开始尚无历史值时要通过 reset、计数器或 guarded property 避免误读。$rose/$fell/$stable/$changed 也按采样值判定。若 antecedent 永远不匹配，implies 属性会 vacuously pass；所以重要断言通常配对 cover property 确认 antecedent 和完整场景确实发生。

5.3 disable iff、重复与边界

disable iff (reset_expr) 在 reset 条件有效期间中止/禁用进行中的 property evaluation，常用于异步复位屏蔽；它的表达式求值语义与属性主体的 sampled operands 不完全相同。若 reset 同时钟边沿变化，必须明确希望取消还是检查该样本，并通过专门测试验证。

重复操作符要分清：[*n] 要求连续匹配 n 次；[=n] 是非连续重复，允许匹配之间有不匹配的采样点，也允许在最后一次匹配后出现尾随的不匹配采样点；[->n]（goto repetition）允许前面的间隔采样点不匹配，但匹配在第 n 次出现处结束。first_match(sequence_expr) 选择从当前起点开始最早结束的匹配；它不是对任意歧义的通用消除器，也不会让不匹配的属性变成匹配。仅当后续组合需要明确选定首个结束点时使用它，并用反例验证语义。

sequence two_cycles_high;
  valid[*2];
endsequence

property no_accept_without_valid;
  @(posedge clk) disable iff (!rst_n)
    accept |-> valid;
endproperty

c_valid_seen: cover property (@(posedge clk) valid ##1 accept);

对 [m:n] 的边界至少验证 m-1、m、n、n+1 对应行为（需根据 property 结构区分 antecedent/consequent 起点），unbounded ##[1:$] 可能一直等待而不失败；是否要求 eventually、是否有限仿真结束前要结束，需用有界要求或 strong semantics，并配置适合的 formal/simulation 策略。

DRAM 对应方式： 把已批准的“命令 A 后命令 B 不得早于 N 个采样周期”转为属性时，先定义起点事件、目标 bank 比较、边界的包含性、模式条件和复位中断。$past 只看前一采样点，不能代替任意周期历史；复杂同 bank 事件通常需要显式 monitor/state 或 sequence 参数化。

练习：构造 property：start 后 2 周期内必须看到 done；让 start 永不拉高观察 assertion 与 cover 的结果。答案线索：assertion 可能 vacuous pass，cover 用来证明场景发生；分别考虑 |->/|=> 对第一个允许周期的差异。

6. functional coverage：定义观测目标，不替代 checker

6.1 covergroup 和采样方式

covergroup 可以由 event 自动采样，也可显式调用 sample()。coverpoint 观察值并映射到 bins；cross 观察多个 coverpoint 的组合。

covergroup cmd_cg @(posedge clk);
  option.per_instance = 1;
  cp_cmd: coverpoint cmd iff (cmd_valid) {
    bins act = {ACT};
    bins rd  = {RD};
    bins pre = {PRE};
  }
  cp_bank: coverpoint bank iff (cmd_valid) {
    bins each_bank[] = {[0:3]};
  }
  cmd_by_bank: cross cp_cmd, cp_bank;
endgroup

trigger event 决定采样时刻；coverpoint/covergroup iff 决定此样本是否参加覆盖统计，不是断言条件，不会让仿真失败。必须确认 event 上的 payload/state 已稳定；同一 event 触发多个 listener 时不能假设它们按源代码顺序执行。

显式 sample 可把采样参数设计为快照：

covergroup observed_cg with function sample(
    input teach_cmd_e sampled_cmd,
    input bit [1:0] sampled_bank);
  cp_cmd: coverpoint sampled_cmd;
  cp_bank: coverpoint sampled_bank;
endgroup

observed_cg cg = new();
// 在 monitor 已形成稳定 transaction 后调用：
cg.sample(tr.cmd, tr.bank);

这比 covergroup 直接读取一堆可能变化的层次信号更容易测试。covergroup 构造参数也可用 ref 绑定外部变量：

bit [3:0] live_addr;
covergroup live_cg(ref bit [3:0] addr_ref);
  cp_addr: coverpoint addr_ref;
endgroup
live_cg live = new(live_addr);

该实例在它的采样时刻读取被引用的变量；ref 不会为每个 transaction 自动保存历史快照。若想快照，通常用前面的 sample 参数传值更清晰。某些工具/语言版本对构造参数和 sample 参数的支持细节需核对 LRM 与工具手册。

6.2 bins、cross、ignore_bins、illegal_bins

covergroup timing_cg with function sample(int unsigned delta);
  cp_delta: coverpoint delta {
    bins below = {[0:3]};
    bins exact = {4};
    bins above = {[5:8]};
    ignore_bins outside_model = {[9:$]};
  }
endgroup

bins 将数值或转移映射成命名目标；数组 bins 可以自动为值域拆分 bins；transition bin 可写 (IDLE => BUSY)。cross 的理论组合数约为两个 coverpoint bin 数相乘，维度多时会爆炸。用 binsof/intersect 或 cross bins 精确限制有意义组合，不能因为交叉巨大就全盘删除它。

ignore_bins 是明确排除、不计入目标的组合；illegal_bins 把不应该出现的覆盖值标记为 illegal bin，工具通常报告观察到该值，但它不替代一个具有明确报错级别/诊断内容的 assertion。非法协议必须由 checker/assertion 明确检出。不要用 illegal bin 作为唯一协议检查。

transition bins 统计观测序列，如 bins closed_to_open = (0 => 1);；它是 coverage 状态转移，不会保存协议必须依赖的完整历史状态。参数化 bins 时避免把地址空间每一个地址都拆成独立 bin，除非需求确实要求逐值覆盖。

6.3 get_coverage 与 coverage 收敛

coverage 方法能查询 coverage 数值，例如实例 coverage 与类型/组 coverage；get_inst_coverage()用于实例层级查询，get_coverage()常用于 covergroup/type 汇总。示意调用为 real inst_pct = cg.get_inst_coverage();。多实例的百分比聚合方式受 coverage option 和工具实现影响，读报告时要知道看的是什么范围。

coverage 达到 100% 只表示当前定义的 bins 被命中，可能仍有遗漏需求、错误的 iff、未覆盖非法路径或被误设 ignore 的 corner case。每个 bin 应追溯到验证计划场景。建议保存 simulator coverage database 和 text report，并为每条未达目标 bin 提供未达原因/刺激计划。

DRAM CoverageModel 对应： package 中的命令 enum 和 event 是 coverpoint 输入；命令事件是采样拍；bank/address/state/timing condition 可成为 coverpoint；cmd×bank 或 mode×timing-condition 是 cross。约束激励负责让场景发生，assertion/checker 负责判定合法性，covergroup 负责统计已观察场景。不要把参考项目里的自动生成 bins 当成规范权威。

练习：定义 RD/W R 命令 bins、4 个 bank bins、命令×bank cross；给每个 bin 写需求/场景 ID，并构造一个 RD 已全覆盖而 cross 仍缺组合的序列。答案线索：先区分单点覆盖与组合覆盖；检查 iff 是否在无效命令时抑制样本。

7. package、import、编译单元、bind

7.1 package 和 import

package 是显式命名空间，适合放共享 typedef、参数、函数和 class 定义。IEEE 1800-2023 §26.2 也允许 package 声明 SVA sequence、property 和 checker；但 package 是声明作用域，不是 module/interface，不能直接放置独立运行的 concurrent assertion 过程（需要在合法的验证作用域实例化/执行）。不要把 sequence ... endsequence 这种 SVA 时序表达式声明，与 UVM uvm_sequence 这样的 class-based stimulus 生成对象混为一谈：同名不代表同一构造，前者描述信号匹配序列，后者运行 transaction sequence。IEEE 明确允许 package checker 声明；“checker 不能放 package”并不准确，但工具对标准构造的支持要按兼容表确认。其它作用域可写 import pkg::type_name; 或 import pkg::*;。显式 import 更易发现依赖；wildcard import 若多个 package 提供同名符号，可能造成歧义或意外绑定。构建脚本应明确先编译依赖 package。

package teach_pkg;
  typedef enum bit [1:0] {ACT, RD, PRE} teach_cmd_e;
  parameter int unsigned NUM_BANKS = 4;
endpackage

module top;
  import teach_pkg::*;
  teach_cmd_e cmd;
endmodule

7.2 compilation unit 与 timeunit

compilation unit 是工具编译组织边界，可能是一个源文件，也可能由命令行把多个文件组合处理；不同工具选项会影响边界。未放在 package/module/interface/program 中的 compilation-unit scope 声明，对同一编译单元内源文件可见，但不应当成跨工程稳定 API。共享类型优先放 package。

用显式 timeunit / timeprecision 控制时间单位/精度，避免依赖 timescale 文本顺序产生隐藏差异。timeunit 1ns; timeprecision 1ps; 决定当前作用域的时间比例/精度；#1step 是特殊同步步长，按全局精度定义。跨文件工程要固定编译顺序和 timeunit 策略。

7.3 bind

bind 把 checker/assertion/interface 实例绑定到现有 module instance/type 层次，无需直接修改 RTL 源码，适合在验证环境中附着 protocol checker。

module req_checker(input logic clk, rst_n, req, gnt);
  property req_eventually_granted;
    @(posedge clk) disable iff (!rst_n) req |-> ##[1:4] gnt;
  endproperty
  assert property (req_eventually_granted);
endmodule

bind dut req_checker u_req_checker (
  .clk(clk), .rst_n(rst_n), .req(req), .gnt(gnt)
);

实际 bind 的可见信号、参数覆盖、generate 层次和编译支持要在目标工具验证。不要为了“用 bind”绑定不能解释来源的 checker；每条属性仍须有需求追踪。

7.4 program：测试平台调度构造

program 是 SystemVerilog 的 testbench 构造，其过程按 Reactive 区域语义运行，设计代码通常在 Active/NBA 等区域更新；它最初用于减少 testbench 和 DUT 在同一仿真时刻读写造成的竞争。它不是 UVM 的必需容器，也不是万能 race 修复器：clocking block、采样区域、transaction 调度与组件架构仍需明确。现代环境可用 module/interface + class/UVM 组织 testbench；若现有项目用了 program，要读懂其调度含义，并确认 simulator 支持和团队约定。

program automatic simple_test(simple_if.TB bus);
  initial begin
    @(bus.drv_cb);
    bus.drv_cb.req <= 1'b1;
  end
endprogram

这段只表示 program 的常见结构形状；一个具体 interface/modport 是否可按该端口形式连接，应按工程声明和工具诊断核验。不要因 Reactive 区域就认为程序内所有过程之间有顺序保证。

8. DPI、VPI 与高级调试

8.1 DPI-C

DPI（Direct Programming Interface）连接 SystemVerilog 与 C/C++，适合调用成熟算法、参考模型、日志/数据处理库。import "DPI-C" 从 SV 调用 C 函数；export "DPI-C" 允许 C 回调 SV。声明方向、宽度、signedness、string、open array 和对象生命周期都需按 DPI 类型映射核对。不要从 C 侧直接并发改仿真信号；通过明确 API 返回数据，再由 SV 在合法仿真调度点更新。

import "DPI-C" function int unsigned crc32(input byte unsigned data[]);

int unsigned value;
initial begin
  byte unsigned bytes[4] = '{8'h01, 8'h02, 8'h03, 8'h04};
  value = crc32(bytes);
  $display("crc=%08x", value);
end

此处是接口形状示意，C 函数原型需遵循工具生成的 DPI header 和标准映射；不要只凭 SV 声明手写 ABI。DPI 函数若可能耗时/阻塞或回调仿真器，要用 context 等正确属性并了解工具限制。纯计算通常保持无副作用，便于重放和调试。

8.2 VPI

VPI 是 C 层访问仿真器对象模型的接口，可遍历层次、读写对象、注册回调、接入外部调试/波形工具。它比 DPI 更贴近 simulator 内部对象句柄，适用于调试自动化、外部接口适配和工具插件，不适合作为一般 transaction 模型的首选。跨仿真器可移植性、回调时机、对象优化/访问权限和性能都是实际限制。

8.3 调试方法

  • 每个 randomize 失败打印 seed、约束 mode、关键状态与 rule ID，并保留最小复现序列。
  • 先打印结构化 transaction（使用 %p 或自定义 convert2string()），随后再展开信号波形；不要只检查大段 raw bus。
  • 失败报告包含当前 event、相关历史 event、计算差值、门限和单位。
  • 用波形检查信号实际值、clocking sample、SVA sampled value、state update 和 covergroup sample 的相对顺序。
  • assertion 报错时区分失败采样与 action block 读取时的实时变量；并发 action 可能已看到后续更新。
  • coverage 低时检查 stimulus 是否发生、monitor 是否识别、iff 是否打开、bin 边界是否合理、report 是否查看了正确实例。
  • DPI/VPI 问题先缩成一个函数/回调，再加入真实工程；检查 C ABI、共享库路径和 simulator 加载参数。

9. 贯穿 DRAM 验证的语言分工

一个可维护的检查流可以这样划分：

  1. interface/clocking block 约定 CK/CA 的驱动与采样边界。
  2. monitor 把 pin activity 转为 raw sample 和 transaction。
  3. decoder 按批准协议定义识别命令，保留无效原因和时间信息。
  4. 状态模型保存 bank/rank/sub-channel 历史；纯函数计算单位换算与间隔。
  5. assertion/checker 根据历史关系检查协议规则；报告准确指出需求条目和两端命令。
  6. stimulus class 通过约束产生有效场景、边界场景和错误场景；randomize 失败显式处理。
  7. functional coverage 按稳定 event/transaction 采样，统计命令、状态、模式、时序类别和有意义的 cross。
  8. regression seed、coverage DB、错误日志和波形形成可复现证据链。

在你指定的 LPDDR6 参考代码里，可以把这些概念映射到 package 类型、interface 采样/decode、命名事件、状态/timing 派生和 coverage include；阅读结论仍需回到权威需求确认。参考文件很大也不是证明其结果正确的证据。

10. 综合练习和答案线索

练习 A：复制语义

transaction 有一个嵌套 class 字段。做 copy = original 后改副本，观察原对象是否变化；实现 clone 并重试。

答案线索：首先是 handle 复制；深拷贝要为嵌套对象单独 new 并复制内容。

练习 B：约束一致性

约束 cmd==RD -> bank_open[bank]，再将 bank_open 全置 0，并要求 cmd==RD。记录 randomize() 返回值。

答案线索：硬约束无解要返回失败；soft 默认值不能使互相矛盾的硬约束神奇地可满足。

练习 C：并发通信

用 named event 通知一个 consumer；先触发再启动 consumer；再换 mailbox 保存 item。

答案线索：裸 event 不是队列，可能错过此前触发；mailbox 能保留尚未消费的对象，注意传的是 handle。

练习 D：时钟边界

用 interface + clocking block 驱动 req、采样 gnt；分别记录无 clocking block 与 input #1step 下边沿附近波形。

答案线索：先查清驱动 skew、采样 skew和区域调度；#1step 采边沿前一个精度步，不是周期延迟。

练习 E：SVA vacuity

建立 req |-> ##[1:2] ack，运行 req 从未拉高和 req/ack 正常序列两种情况，同时加 cover property。

答案线索：没有 antecedent match 时 assertion 可能 vacuously pass；cover 用来确认检查场景发生。

练习 F：coverage 与 checker

构造非法命令让 covergroup 命中 illegal_bins，观察工具报告；另加 assert property 检查禁止场景。

答案线索：coverage bin 是覆盖模型分类/报告；assert 才是明确检查路径。工具对 illegal bin 报告可配置，不能用它取代 checker。

11. 与个人参考项目和学习目录的关系

这篇文档提供可复用的语言语义和验证构件，不预设 UVM。你可以先独立写 transaction class、monitor、checker 与 covergroup，再逐步看 UVM 怎样组织同一类组件。UVM 是基于 SystemVerilog 的验证方法学/类库，不是学习这些语言特性的前置条件。

参考项目精读带你读 LPDDR6 coverage 生成结果；独立实现 CoverageModel讲从批准需求设计自己的模型；教学实验中的 labs/04_coverage/tb.sv 使用简化 ACT/RD/PRE 命令练事件、同 bank 间隔与边界计数，不代表 JEDEC 命令编码或规范行为。真实项目必须以适用版本的正式规范、勘误和项目批准需求为准。

本讲义未编译或运行所列片段。具体支持范围会随仿真器、版本和编译选项变化；例如厂商支持表中可能有个别标准特性标成不支持。遇到工具差异时，记录最小复现、仿真器版本和诊断信息，再对照 IEEE LRM 的规范语义与工具 release notes。
